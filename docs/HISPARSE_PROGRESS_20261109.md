## 部分前缀命中时，真正跳过对应换入

审查发现：此前部分命中的请求仍把完整 Top-K 交给原生 swap，之后才用 donor 的
GPU 槽位覆盖命中位置。输出引用了共享 KV，但不能据此声称那些位置已免去原生 staging。

现在在调用原生 swap 前，将可直接读取的块标记为 `-1`，保留 Top-K 的形状和顺序，
原生处理剩余位置后再合并结果。全命中行不调用 swap；最新 token 所在块仍由原生
保留槽处理。固定版本 CUDA 内核对负位置在哈希表、LRU 和 miss-copy 前进行排除；
启用直接复用时同时检查该内核与 Python 包装器的原始 SHA256。

新增测试实际调用共享换入 helper，检查送给原生函数的块、最终输出、全命中、部分
命中、最新 token、无效块和无 donor 的情况。统计项
`shared_prefix_masked_native_blocks` 表示部分行中从原生调用排除的块数，
不等于实际 H2D 字节：原生热池中的命中本来就可能不发生数据传输。
GPU 正确性、实际流量与 TPOT 仍需单独验证。详见[共享前缀实现](SHARED_PREFIX_RUNTIME.md)。

## 真实模型 profiler 的执行入口

新增 `--profile-workload`，在指定 workload 预热后开启固定镜像自带的 PyTorch
Profiler，捕获相同请求，再停止并等待四个 TP rank 的 trace 写出。默认每请求最多
生成 16 token，可设置 1–32；关闭 stack 和 shape 记录以限制诊断规模。

分析器要求每个 rank 都有 CPU 算子和 CUDA kernel；统计各内核耗时、GPU 活动区间
的并集与耗时总和、同步 API 的 CPU 调用时间、可见的显式 memcpy。并发 GPU 活动
不能简单相加当作端到端时间；stream-wait API 的 CPU 耗时也不等于 GPU 等待时间。
HiSparse 可在内核里读取 mapped host memory，因此显式 memcpy 字节不是完整 H2D 流量。

诊断运行与正式性能测量互斥，manifest 带诊断标记，汇总器拒绝将其纳入吞吐对照。
当前已完成控制接口、异常清理、四 rank trace 覆盖、区间统计和过滤规则的 CPU 验证。
**完整 MiniMax 的 GPU trace 尚未采集**。现有真实 GPU trace 来自单卡 VMM/Graph
映射测试，二者不能混同。[使用说明](HISPARSE_PROFILING.md) ·
[已完成的单卡验证](CONTAINER_VALIDATION_20261109.md)

### 统一入口的 spawn 缺陷

静态组首次恢复启动后，在模型加载前被 SM90 最低能力检查拒绝。根因是
`python -m elastic_kv` 的入口是包的 `__main__`；Python multiprocessing spawn
不会重建这种模块，因此 worker 没有执行原有的 SM80 投影适配。这个问题也可能影响
依赖同一导入入口的其他 worker hooks，CPU 中直接调用安装函数的测试不能覆盖它。

已将实验 runner 改为 `python -m elastic_kv.launch`，包入口也通过 `runpy` 暴露
实际启动模块。新增测试启动真实 spawn 子进程，以每个进程自身 PID 核对安装行为：
旧包入口可复现失败，两个修正入口均通过。容器完整 CPU 测试更新为 599 passed、
3 skipped，另有 186 subtests passed。失败结果保留，后续采用新目录重试；仍须由
真实模型启动和推理验证这些 hooks，而不能只凭这项 CPU 回归宣称已恢复性能对照。

### 加载期间的外部占用使本轮容量失配

修复入口后的 r4 已完成四卡模型加载、服务预热并返回健康状态。运行期间的 GPU PID
监控记录到外部程序进入选定卡：先有 46 次仅自有计算进程的采样，随后 18 次包含
外部计算进程。首次观测到干扰在 08:34:12 UTC；模型在 08:35:41 加载结束。
08:35:50，原生 SGLang 将请求的 32,768 token 设备池缩减为 14,208。
08:36:06，runner 的实际容量校验失败并关闭自有服务，没有开始语义探针或正式计时。
这次结果不能填入性能表，也没有调小容量来强行通过对照。

该记录证明，启动前连续空闲检查不能保证整个运行窗口独占。后续控制器增加运行期间
的容器归属与 GPU PID 核验：同一外部 PID 连续两次出现时，先重新确认自有容器身份，
再仅停止该实验容器。即使只观测到一次干扰、任务最终正常结束，也排除该臂结果。
无法确认归属的采样会单独记录，不据此停止进程。它仍是周期观测，不是 GPU 资源锁。
失败目录保留，新尝试使用新目录；没有停止或修改外部程序。

r5 的实际运行验证了这条保护路径：通过空闲门禁后，另一组 vLLM worker 进入八张卡，
控制器连续两次观察到四张选定卡上的外部计算 PID，在启动约 22 秒后停止并移除了
经身份核对的自有实验容器（wrapper 退出码 143）。外部 worker 保持运行，每卡约
58,810 MiB。该轮同样没有性能结果；它是资源冲突检测的实际验证，不是显存机制收益。

## 后续目标：按 query 波动与缓存收益调整请求热集

用户新增研究目标：研究为波动较大的 query 分配更大 HiSparse GPU 驻留集是否有益。
它排在当前正式对照与 profiling 之后；不改变正在等待的九臂参数。当前实现是在
原生有界热集和完整 GPU KV 之间切换，尚未实现每个请求拥有不同中间容量 `t`。

先区分两种信号：实际 indexer query 的相邻步 cosine drift，以及逻辑 Top-K 集合
的变化。后者可按请求、层和选择组统计 Jaccard turnover、新进入块比例与复用距离。
不能默认 attention query 就是 indexer 的 query；现有 capture 也不足以覆盖这个实验。
诊断时保留正确的层、步和 TP 分片身份，剔除无效槽，并单列最新 token 保留页。
在线策略优先在 GPU 上聚合 Top-K 统计，避免每层搬 query 到 CPU 引入同步。

研究假设不是“波动越大，容量越大越好”。例如两个工作集周期交替，增加容量可能
避免反复换入；若持续访问此前从未出现的新块，扩大有限缓存可能几乎无效。
先采集真实选择轨迹，回放固定版本 LRU，估计增加一档容量后减少的 miss 数与字节。
用历史窗口预测后续窗口，避免把未来真实选择泄漏给在线策略；离线最优只作上界。
这也与工作区的 Top-K/Miss 预测调研互补：重点是**新增 HBM 能减少的实际换入**。

固定镜像的 `hisparse_coordinator.py` 使用全局 `device_buffer_size` 建立请求槽和
逐层 LRU，并在热集后放置最新 token 保留页。该容量还是 `hisparse.py` / `hisparse.cuh`
的 JIT 模板参数，影响扫描范围、共享内存和槽索引。VMM 可提供物理预算伸缩，
但不能仅靠补映射就让这些固定容量内核自动支持不同 `t`。
首版先仅对长请求在准入时分配少数预编译、页对齐的容量桶；每桶必须容纳展开后的
Top-K，并经过共享内存和索引范围验证。随后才研究运行中升降，处理最新 token 页、
逐层 LRU、host 备份、旧物理页释放以及 TP 一致提交，加入最短驻留时间和升降阈值。

公平对照固定逐卡峰值 HBM 预算、请求流、Top-K、输出长度和并发，比较原生统一 `t`、
等预算静态分桶、在线分桶与离线容量分配上界；再单独测增加并发后的容量收益。
同时报告 miss、实际 host 读取、VMM backing、整卡 NVML、吞吐、TTFT/TPOT 尾部，
以及额外 kernel launch、扫描和迁移开销。扩大热集可能增加管理成本或挤掉其他请求，
不能仅凭命中率升高判定更快。容量分配按实际物理 chunk 的增量和可回收字节计费，
不能假设减小逻辑 `t` 就等量归还 HBM；若无法读取硬件流量计数，只报告逻辑 miss
字节，不能把它称为 PCIe 实测。以上是待执行的研究计划，尚无收益数据。

SQLite 导出；数据库中能找到预期的完整标记区间。开发容器中的同类检查也通过。
首次固定容器尝试把工具目录改名为 `/nsys` 被 CLI 拒绝，保留 `target-linux-x64`
目录名后通过，失败记录保留。该检查验证采集与导出流程，不是 CUDA 或模型性能证据。

单卡 VMM/Graph 测试新增 `--profiler-backend nvtx`：只发 NVTX 区间，由外部 Nsight
采集，避免同时开启 PyTorch Profiler；默认 Torch 模式保持原行为。NVTX 模式沿用
原有映射、回收、重映射和旧 Graph replay 正确性检查，但这些 GPU 步骤尚未以
新模式运行，结果也不会虚构外部 trace 已通过。

离线分析器此前只保留 wait 类 CUDA API 的 CPU 统计，现在同时保留观察到的全部
Driver/Runtime API，便于检查 VMM API 开销。针对性测试验证：即使 CPU 上有很长的
`cuMemCreate` 等调用，GPU 区间并集也不受影响。空字典不能证明没有 VMM 工作；
swap 内核次数也不能换算为 miss 或迁移次数。原始 trace、实际动作计数和关联信息
需要共同用于归因，不能将 kernel 耗时求和当作关键路径。当前冻结的 r6 不受这些
诊断脚本修改影响。[采集说明与记录](HISPARSE_PROFILING.md)
